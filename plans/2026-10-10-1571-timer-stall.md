# Trace the 1571 Timer 1 load-stall discrepancy

Lane: engineering-frontier accuracy. Issue 1679 asks why the previously
corrected one-cycle Timer 1 load error stalled Bruce Lee on the 1571 while
the 1541 still loaded. The retained motor/head traces establish the symptom,
but do not identify the responsible ROM branch or timer access.

1. Use a detached worktree of the integrated VIA/light-pen tree. Keep the
   source PR and its running catalogue validation unchanged.
2. Add temporary observational tracing to
   `crates/machine-commodore-1571/src/lib.rs`: timer accesses, motor/head
   transitions, job-status writes and relevant drive RAM state. Read pins
   and use side-effect-free peeks; do not add emulator clocks.
3. Add an explicit negative control at the existing Timer 1 high-write
   load stage in `crates/mos-via-6522/src/lib.rs`. When enabled, restore the
   former same-cycle decrement; leave all other behaviour unchanged. This
   control is diagnostic only and will not enter production.
4. Run the same mirrored Bruce Lee 1571 catalogue guest with and without
   the control. Retain command, source/patch/firmware identities and traces.
   Require the old stall to reproduce before treating this as causal
   evidence; unchanged success would invalidate this control as a repro.
5. Compare the first differing job/drive event, then trace the associated
   ROM instructions against the staged official 310654-05 image, the
   primary drive references and VICE's board/timer implementation. Do not
   close issue 1679 from successful loading alone. Any new production fix
   needs a separate failing regression and explained mechanism.

The existing primary references are *The Anatomy of the 1541 Disk Drive*
(job loop $F99C, stepper $FA81/$FAAB) and *Die Floppy 1571* §11.1 (different
SYNC timeout loops in 1541-compatible and 1571 modes). The 1571 ROM itself
must establish which paths this guest uses; those descriptions alone are
not an explanation of the stall.

## Reproduced cause and bounded correction

The early-T1 negative control reproduces the historical failed frame/audio
hashes exactly. Its disk-job completion sequence is an exact prefix of the
successful run. At drive cycle 160142709, ATN raises VIA1 CA1 (IFR $40 ->
$C2) while the ROM is at $81BC (`LDA $180F`). Before the next recorded
port-B write, CA1 is gone and software attention flag $7C is still zero.

Both 1541 and 1571 machine read paths map port A registers $1 and $F to
`read_port_a_with_value`, which unconditionally acknowledges CA1. The chip's
ordinary `read($F)` correctly preserves it. *Die Floppy 1571*, printed p114,
explicitly identifies $180F as the no-handshake register; its p212 listing
identifies this ROM path (the official ROM bytes verify the instruction).
VICE `viacore_read`, `VIA_PRA_NHS`, likewise skips the acknowledgement.

1. In a separate branch, add regression tests in
   `crates/machine-commodore-{1541,1571}/src/lib.rs`. Exercise both VIAs,
   every decoded mirror and IEC-aware/standalone reads: the alternate read
   preserves a raised CA1 IRQ and returns the same pins; the normal read
   acknowledges it. Demonstrate failure before the correction.
2. Keep board-specific port sampling and rotation unchanged. Call the
   acknowledgement helper only for register $1; return the sampled pins
   directly for register $F. No new API, state or architecture is required.
3. Run both drive suites, affected Clippy and formatting. In the diagnostic
   worktree, repeat the early-T1 control with this correction and preserve
   the post-edge trace. Recovery with the intentionally wrong timer will
   test whether the lost attention request actually caused this stall.
4. Validate affected C64 catalogue disk guests and snapshot replay on the
   production correction. Retain exact before/after evidence without ROMs.

## Same-edge causal result

With the early-T1 control still enabled, the board correction reaches the
same ATN assertion at cycle 160142709. At 160142712 the ROM reads $180F
with IFR $C2; at 160142718 its following $180F write still sees IFR $C2.
The CPU fetches the IRQ vector at 160142753/754. The handler reads $1801
at 160142799 and writes $01 to $7C at 160142804; the command loop reads
that flag at 160142870. Thus the correction preserves precisely the
request that the old decoder lost. The disk proceeds beyond halftrack 14.
The completed early-timer run recovers the exact working sequence of
3,114 job writes and 138 motor/head events. The failed run has 2,945 job
writes and 102 motor/head events, ending at halftrack 14. Both successful
sequences end at halftrack 22. The fixed negative control reaches game
code ($208D at frame 20,000); the failure remains in KERNAL serial input
($EEB1). Because the negative control retains an incorrect timer, its
frame/audio hashes differ from the production goldens; it is not a
catalogue pass.

The production change is source PR
[1696](https://github.com/emu198x/emu198x/pull/1696), commit `05de4cf9` (rebased from `35456d50` onto merged main with an
identical tree).
The two added regressions fail on the parent with
`alternate read 180f, IEC=false, lost CA1` (left 0, right 130). After the
fix, 145 drive tests pass, as do all-target Clippy and workspace formatting.
Each regression covers 64 combinations: two VIAs, 16 mirrors and two read
paths. A fresh production build is running all 13 C64 catalogue entries
in three non-overlapping shards, including snapshot replay. No expected
hash has been edited.
