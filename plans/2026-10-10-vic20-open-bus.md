## Measurement result

The full guest completes on PAL and NTSC with a passing stability guard.
All 512 raster-register bytes agree with both matching physical dumps.
All 512 open-bus bytes disagree with each dump: Emu198x returns `$FF`
throughout. The NTSC header differs only in the guest revision identifier
(R01N versus the captures' R01C). No comparison bytes are excluded.

Native VICE xvic 3.10 is also wrong in this measurement. Its `$9100` samples
are all `$91`, and its `$9200` samples all `$FF`:

| Hardware dump | Native `$9100` differences / 256 | Native `$9200` differences / 256 |
|---|---:|---:|
| PAL 6561E | 162 | 256 |
| PAL 6561-101 | 255 | 256 |
| NTSC unspecified 6560 | 255 | 256 |
| NTSC 6560-101 | 171 | 256 |

The raw hardware pairs themselves differ at 93 PAL or 84 NTSC positions per
open-bus column: `$91`/`$92` versus `$20`. Do not select one physical dump
as a universal oracle or infer a chip-revision switch without tracing the
board and capture differences. Original provenance and identities are in
`198x/reference/by-system/commodore-vic20/2026-open-bus-measurement-observations.md`.

## Root-cause boundary and next work

`Vic20::mem_read` explicitly returns `$FF` for these addresses. Neither the
machine nor VIC-I stores the CPU/video bus history needed to return fetch
data. `Vic::render_cycle` reads screen and character memory for pixels and
skips rendering outside the framebuffer. Those calls cannot serve as bus
transactions: they repeat within a cell and do not cover the complete raster.

VICE provides useful precedent for distinct CPU and video bus values and an
alternating matrix/character fetch state machine (`vic-cycle.c`). Its I/O
decode does not reproduce these hardware readings: `$9100` falls through to
the retained CPU byte; `$9200` is in the VIA I/O handler's range but has
neither A4 nor A5 asserted, so `via1_via2_read` returns `$FF`. Copying either
path would leave most hardware samples wrong.

The next step is to trace board bus buffering and the VIC-I fetch sequence,
including idle cycles, using the original guest and primary wiring evidence.
A complete fix needs timed fetch state and retained bus values, not a
constant-address heuristic or calls attached to pixel painting. The exact
stage design and snapshot schema remain undecided and unapproved; no
production prototype is retained.

## Verification and retained evidence

The diagnostic is `survey_timing_measurements` in the existing VIC-I survey
test. It pins guests and all four physical dumps, requires the guest's done
flag and stable-raster result, asserts all raster-register control bytes and
records all five sections' mismatch coordinates and values. A successful
diagnostic means the measurement completed, not that open-bus accuracy passes.

Both native captures reproduce byte-for-byte in a second run. Deliberately
changing the first emulated `$9003` sample makes the control assertion fail

tests, targeted Clippy, formatting, fixture guards, ignore-reason check and
documentation links are the source checks for this measurement-only change.
The evidence folder includes original failed native-monitor setup output:

## Bus-cycle trace and fetch-phase closure

An observational patch recorded the CPU data-read phase of every measurement:
2,048 reads across the two guests. It captured the VIC registers and the
measurement's screen/character RAM at each read. Applying and then removing
that instrumentation left both complete result buffers byte-identical to the
unmodified diagnostic. No production state or timing changed.

The reference fetch schedule starts matrix access at horizontal origin plus
four cycles, then alternates matrix and glyph reads for the latched columns.
Applying that schedule to the observed bus clocks and guest memory explains
all 1,340 active-fetch samples across the four physical dumps. It also matches
all 354 idle samples in the 6561E and 6560-101 dumps when idle leaves the last
CPU operand byte on the bus. Thus those two complete 512-byte open-bus scans
are explained without excluding samples or fitting a pixel shift.

The other two dumps disagree in exactly the remaining 354 idle samples: each
has `$20`. The active fetches are identical. A board/chip/power-on mechanism
for that idle difference is still unresolved. Do not add a `$20` constant or
assign the difference to a chip suffix. The measurement does not include the
complete original machine memory or a trace of its idle address lines.

Moving the proposed fetch phase by one cycle in either direction breaks the
comparison. The retained analysis reports these negative controls separately
from the unchanged emulator's still-failing output. This is a causal model
checked against measurements, not an implemented correction.

Commodore's original 324001 schematic in technical manual P/N 990440, printed
sheets 2–4, shows the CPU and video address/data paths separated by buffers;
the data transceiver is enabled and directed by CPU R/W. The primary note
records the scan URL and byte identity. This supports a video-bus contribution
to CPU reads; it does not explain the two idle behaviours by itself.

The evidence is in `2026-10-10-vic20-fetch-phase/`. Remaining design work must
cover timed matrix/glyph latches, row/address counters, the CPU/video bus
values and pixel delivery from the same fetched bytes. Existing pixel-time
callbacks cannot supply that contract. Snapshot layout approval is still
required before implementing those retained stages.

## Proposed retained-stage correction — approval required

Extend the existing VIC-I and board state; keep the CPU pin interface,
oscillator cadence and framebuffer dimensions. This is a correction to the
missing fetch mechanism, not a new machine or a replacement CPU/video core.

1. In `crates/mos-vic-i/src/lib.rs`, retain horizontal/vertical fetch enable,
   the four-cycle start delay, alternating matrix/glyph phase, cell index,
   row/address counters and latched matrix/colour/glyph bytes. Service one
   actual memory fetch per applicable cycle across the entire raster,
   including cycles outside the captured framebuffer. Use the existing
   column/row latch schedule and the inspected reference's counter ordering.
2. Drive pixels from those fetched bytes, with the cell's output position and
   timed colour state retained until delivery. Remove pixel-time memory
   rereads. Trace first/last cells, line wrap, 8/16-line characters and live
   origin/column/base writes before accepting output changes. Do not shift
   a finished image or retain a second independent display-memory model.
3. In `crates/machine-commodore-vic-20/src/lib.rs`, retain the CPU and video
   bus values, update them from actual CPU/VIC accesses, and resolve
   unselected/partially driven reads through the board wiring. Check I/O
   selection and mirrors against the schematic; preserve read side effects
   and non-mutating host peeks. The known retained-operand idle behaviour
   supplies the initial board contract. Keep the unexplained `$20` captures
   as explicit residuals; add no fabricated idle-byte or chip-suffix rule.
4. Serialize every new latch/counter/output descriptor. Stack on the already
   approved VIA correction (VIC-20 snapshot 8) and advance
   `crates/runtime-commodore-vic-20/src/snapshot.rs` to **version 9**, rejecting
   versions 7/8. Add snapshot continuation on both sides of a matrix fetch,
   glyph fetch, line wrap and live register write in the existing machine
   and runtime snapshot tests. Add no `serde(skip)` to live state.
5. Require both complete retained-operand hardware scans to match, require
   all four captures' active-fetch bytes to match, and report every idle
   residual. Extend directed tests for selected/unselected bus reads and
   register aliases. Run the full VIC-I survey, explaining every changed
   pixel count against native/reference evidence; run package tests,
   Clippy and formatting. Complete the VIC-20 catalogue/replay gate before
   merging. Issue 1678 stays open until the idle discrepancy is resolved or
   its distinct supported hardware scope is established with evidence.

The alternative is to defer production work until the idle difference has a
physical explanation. The retained-stage correction is recommended because
the active fetch mechanism and the retained-operand behaviour are already
independently constrained. Approval covers this stage/schema design, not an
accuracy claim for the unresolved physical variants.
