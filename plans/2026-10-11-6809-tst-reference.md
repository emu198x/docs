# MC6809 TSTA/TSTB reference qualification

The current two-cycle implementation agrees with Motorola's instruction table
and MAME's bus sequence. The pinned XRoar revision emits three cycles because
its shared memory/register TST path adds two dead cycles unconditionally.
Qualify this exception without changing production behaviour or patching the
vendored reference to produce a desired trace.

## Plan

1. Cite Motorola's instruction table in a primary observation note. Record
   MAME's pinned `TST8` path, register operand read and `dummy_vma` definitions,
   plus the independent 6809Decoder instruction-table corroboration. Keep
   implementation readings distinct from physical measurement.
2. Compile the unchanged full XRoar CPU in a wrapper covering both accumulator
   test instructions and every 8-bit accumulator/CC input (131,072 rows).
   Require its observed three-read sequence and retain output flags. Do not
   rewrite its trace to two cycles.
3. Execute the same inputs through Emu198x public pins at PCs 4000/FFFE/FFFF
   (393,216 runs). Require the primary-specified two-cycle length, MAME's
   opcode/FFFF bus addresses, unchanged registers and complete reference CC.
   Check the next opcode-fetch pins. Retain the probe, outputs and hashes
   under `plans/2026-10-11-6809-tst-reference/`.
4. Exercise the probe with deliberately wrong expected cycle/address values
   to show its guards fail. Confirm complete output size and flag agreement.
5. Publish the evidence and update issue #130's outstanding reference question.
   Leave the existing 192 XRoar diagnostic discrepancies visible and explained.
   No CPU/snapshot/schema change is intended; any newly discovered fault
   requires a separate explained correction.

## Result

All 393,216 public-pin executions pass: full CC agrees with the unchanged
reference; all data registers remain unchanged; the next-fetch pins and the
two-cycle opcode/FFFF bus sequence hold at all three PCs. The reference wrapper
separately confirms its three-read sequence in all 131,072 cases. Deliberately
expecting three cycles or a next-PC read fails with exit 101; logs are retained.

Motorola's [opcode cross reference](https://www.maddes.net/m6809pm/appendix_c.htm)
lists two cycles for both 4D and 5D. MAME revision
`9391e1eff80eb04abd58d48218a1d3b9643c1ea8` corroborates opcode then FFFF:
`base6x09.lst:TST8` adds a second dummy only for memory addressing;
`m6809inl.h:read_operand` returns A/B without bus activity; `m6809.h:dummy_vma`
reads FFFF. 6809Decoder revision `4f7e1846375024888ad7987bd390f434897953cf`
also lists two cycles for these instructions. Exact file hashes are retained.

The pinned XRoar shared TST path unconditionally appends two NVMA cycles,
explaining its extra cycle for register forms. Keep the current core behaviour
and preserve the original diagnostic discrepancy as a reference defect against
Motorola's specification. The corroborating models are not new hardware captures
or proof of every silicon revision/sideband signal. No production code changed.

## Reproduction

With XROAR pointing to the pinned reference checkout:

```sh
cc -std=c11 -O2 -Wall -Wextra -Werror \
  -I "$XROAR" -I "$XROAR/src" -I "$XROAR/portalib" \
  reference.c "$XROAR/portalib/delegate.c" -o reference
./reference > reference-flags.bin
```

Build `probe.rs` against `motorola-6809` at the recorded commit with Rust 1.99,
using the matching rlib and dependency directory as in the earlier indexed
probe. Run it from the evidence directory:

```sh
./probe > actual-flags.bin
python3 verify.py
```

`verify.py` checks exact lengths, full equality against the reference repeated
for three PCs, recorded hashes and both deliberately incorrect expectations.
All results remain unmasked. The reference byte stream is ordered opcode
4D/5D, then accumulator 00..FF, then CC 00..FF. The current byte stream adds
PC 4000/FFFE/FFFF as the outer loop.
